# Benchmark Report — spacing P1 (Linux↔Linux)

**Date:** 2026-11-02
**Build:** static-pie release binary (`contrib/build-static.sh`), commit `b500ee8`
**Test beds:** two Multipass VMs, Ubuntu 24.04 Server (headless), qemu/KVM, on one host bridge (`mpqemubr0`, RTT p50 ≈ 0.19 ms)

## TL;DR

End-to-end latency — physical evdev write → injected uinput event on the
remote machine — over real LAN + mutual TLS 1.3:

| Workload | Median | p99 | Drops |
|---|---|---|---|
| Key presses, sustained ~940 ev/s | **0.69 ms** | 1.45 ms | 0 / 4000 |
| Mouse moves, ~195 ev/s | **0.68 ms** | 1.45 ms | 0 / 500 |
| Same-VM loopback, keys ~940 ev/s | **0.26 ms** | 0.65 ms | 0 / 4000 |

Memory: ~5–7 MB RSS per process. CPU: <1 % of one core at ~1000 ev/s.

## Topology

```
┌───────────────┐  evdev   ┌──────────────────────────────────────────────┐
│ e2e emit-bench│─uinput──▶│ spacing serve (captures, grabs, routes)      │
│ "e2e-kbd"     │          │ spacing-srv  10.234.79.81                     │
└───────────────┘          └───────┬──────────────────────────────────────┘
                                   │ TCP 24800 + mTLS 1.3 + postcard frames
                                   ▼
                          ┌─────────────────┐  uinput   ┌─────────────────┐
                          │ spacing client  │──────────▶│ spacing-virtual │
                          │ spacing-cli     │  inject   │ -input (evdev)  │
                          │ 10.234.79.209   │           │ e2e listen --ts │
                          └─────────────────┘           └─────────────────┘
```

"Loopback" runs co-locate server and client on `spacing-srv` (client HOME
`/tmp/clih`), giving a shared-clock, zero-network baseline.

## Methodology

- `e2e emit-bench <delay_s> <count> <interval_ms> key|mouse` creates a
  virtual evdev device, presses `Ctrl+Alt+1` to switch remote, then emits
  `count` events at `interval_ms`. Each emit logs `E <ts_ns> <seq>`.
- `e2e listen --ts spacing-virtual-input` reads the client's injected
  device and logs `R <ts_ns> <type> <code> <value>` per evdev event.
- Latency = `R_ts − E_ts`, pairing each emit seq with its corresponding
  received event (key press → down+up pair; mouse → one REL event).
- **Clock skew (LAN):** VM clocks drift ~80 ppm relative to each other, so
  a single skew measurement is useless minutes later. Skew was measured
  NTP-style (`remote_ts − midpoint(local)`) in a bracket *around* each run
  and interpolated per-event. Residual error ≤ ~0.3 ms, stated next to
  each LAN figure.
- **Loopback:** emitter and receiver share one clock — exact, no skew.
- Raw logs: [`data/`](data). Analysis: `analyze.py` in this directory.

## Notable finding during benchmarking

The first high-rate loopback run crashed the client with
`frame too large: len=51052549`. Wire-level dumps (`SPACING_WIRE_DUMP`)
proved the client-side reader — `recv_msg` awaited inside
`tokio::select!` against a 100 ms watchdog tick — was **cancellation
unsafe**: the tick dropped the future mid-read, losing bytes already
pulled from the TLS stream; the reader then consumed an `Input` payload
as the next frame's length prefix. Fixed in `b500ee8` by reading through
a persistent `read_buf` + `conn::try_decode` (bytes appended to the
buffer survive select cancellation). Regression test:
`buffered_reader_survives_select_cancellation`. Post-fix: 6/6 loopback
runs and 4/4 LAN runs clean at up to ~1000 ev/s.

## Limitations

- **Headless VMs** — the measured path ends at the uinput device on the
  client. A real desktop adds compositor delivery (~1–4 ms on typical
  Wayland/X11 stacks) which this rig cannot observe.
- **Clock skew bound ±0.3 ms** on LAN figures (loopback figures are
  exact). VM clocks drifted ~80 ppm; numbers are interpolated, not synced.
- **One client.** Multi-client fan-out is untested.
- Rates up to ~1000 ev/s are already far above real typing/mouse load
  (typ. <50 ev/s); headroom was not probed to failure.

## Reproduce

```sh
./contrib/build-static.sh          # static binary for any Linux/glibc
multipass transfer … spacing e2e   # to each VM

# VM-A (server):
sudo ./e2e emit-bench 6 2000 2 key &   # device must exist before serve
sudo ./spacing serve &
# VM-B (client):
sudo ./spacing client --to <A-ip>:24800 &
sudo ./e2e listen --ts spacing-virtual-input > recv.log

# loopback variant: run serve + client on one VM (client HOME=/tmp/clih)
```
